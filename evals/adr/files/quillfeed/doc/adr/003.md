# ADR 003: Storage

## Context and Problem Statement

Quillfeed keeps every article it fetches so that the reader works offline from the feed's host, and so that search covers articles the feed has since dropped. An article is a few fields (title, link, author, dates) and a body of HTML, from 1 KB to several megabytes. Everything else Quillfeed stores is in the SQLite database (ADR 001). Where do article bodies go?

## Decision Drivers

- The database stays small enough to copy while Quillfeed runs.
- Reading one article is one lookup.
- A host with a small disk can cap how much Quillfeed keeps.

## Considered Options

1. Bodies as zstd-compressed files on disk, with one row per article in SQLite that holds the fields and the file's name
2. Bodies as BLOB columns in the SQLite database
3. Bodies in an S3-compatible object store

## Decision Outcome

Chosen: option 1, because it alone keeps the database small. With the maintainer's 2,400 feeds, a year of bodies as BLOBs made a 41 GB database that took 19 minutes to copy; with bodies as files, the database was 310 MB and copied in 9 seconds. Option 3 lost because it adds a service the host must run, against ADR 001's drivers.

Confidence: high that it works; the maintainer's instance has run this way since April. Medium that it is better than option 2 for a small instance, where the database would stay small either way.

### Consequences

- Good, because the database copies in seconds, so a backup can run every hour.
- Good, because a host can free space by deleting old body files, and Quillfeed shows those articles as "body no longer kept".
- Bad, because a backup is now two things, the database and the bodies folder, and they can be copied at different moments, leaving rows whose file is missing.
- Bad, because nothing makes a row and its file change together: a crash between writing the file and the row leaves a file no row names.

### Confirmation

`tests/test_store.py` writes an article and fails if the database grows by more than 2 KB.

## Table layout

Articles are in the `articles` table:

| Column | Type | Holds |
| - | - | - |
| `id` | INTEGER PRIMARY KEY | |
| `feed_id` | INTEGER NOT NULL | The feed it came from |
| `guid` | TEXT NOT NULL | The feed's own ID for the article; unique per feed |
| `title` | TEXT | |
| `link` | TEXT | |
| `author` | TEXT | |
| `published_at` | INTEGER | Unix seconds, from the feed |
| `fetched_at` | INTEGER NOT NULL | Unix seconds, when Quillfeed first saw it |
| `body_file` | TEXT | The body's file name, or NULL once the body is no longer kept |
| `body_bytes` | INTEGER | The body's size before compression |

There is a unique index on (`feed_id`, `guid`) and an index on `fetched_at`. Search uses an FTS5 table, `articles_fts`, over `title` and the body's text, filled when the article is stored.

## File naming

A body's file name is the SHA-256 of the uncompressed body, in hex, with `.zst` appended. Files live under `bodies/` in the data folder, in a subfolder named for the first two hex digits, so no folder holds more than a few thousand files: `bodies/3f/3f9a…c1.zst`. Two articles with the same body share one file. Files are written to a temporary name in the same folder and renamed, so a reader never sees half a file. Compression is zstd level 9.

## Retention

Bodies are kept for 90 days from `fetched_at` by default. The host can change that with `retention_days` in the configuration file; 0 keeps them forever. Starred articles are kept regardless. The fields in `articles` are never deleted, so search by title still finds an article whose body is gone.

## Cleanup schedule

Every night at 03:00 local time, Quillfeed deletes the files of bodies past retention and sets their `body_file` to NULL. It then deletes any file in `bodies/` that no row names and that is more than a day old, which removes what a crash left behind. It runs `VACUUM` on the first night of each month.

## History

We first stored bodies as BLOBs (March). Tomás noticed the nightly backup taking longer each week, and on 2 April it overlapped the morning fetch and the reader stalled for 11 minutes. Spike run 2026-04-09-a moved bodies to files without compression: the database shrank to 310 MB but the bodies folder was 38 GB. Spike run 2026-04-11-b added zstd at level 3 (14 GB), and run 2026-04-12-c tried level 9 (11 GB, with storing an article 4 ms slower), which we kept. We tried level 19 in run 2026-04-12-d but storing took 60 ms an article and the walk fell behind. The two-hex-digit folders were added on 15 April after `ls bodies/` hung Tomás's terminal. Migration from BLOBs ran in release 0.3.0 and its code was removed in 0.5.0.
