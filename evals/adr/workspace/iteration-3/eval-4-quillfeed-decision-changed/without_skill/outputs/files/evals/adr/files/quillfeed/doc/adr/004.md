# ADR 004: Each host has its own fetch queue, with requests to it spaced 10 seconds apart

## Context and Problem Statement

Under ADR 002, one poller walked every feed in turn, so feeds on the same host were fetched back to back. On 6 October 2026, three hosts (two blog platforms and a podcast host), each serving more than 150 of the maintainer's feeds, received about 150 requests in 20 seconds every 15 minutes. They answered 429 and then blocked the instance's address for a day. How do we fetch feeds without overloading any one host?

## Decision Drivers

- No host gets more than one request every 10 seconds.
- A new article shows up within 15 minutes (carried over from ADR 002).
- Fetching must fit in the one process (ADR 001).

## Considered Options

1. A queue per host, each with one worker that leaves at least 10 seconds between requests to its host, with hosts fetched side by side
2. Keep the one poller, and have it sleep 10 seconds between two feeds on the same host
3. Drop polling and subscribe with WebSub, so hosts push new articles

## Decision Outcome

Chosen: option 1, because it is the only option that respects the hosts' limits without making every feed wait on the slowest host: hosts are fetched side by side, so the spacing on one host does not delay the others. Option 2 lost because Tomás ran it against the maintainer's 2,400 feeds and one walk went from 6 minutes to 70, so a new article could take over an hour to show up. Option 3 lost because only 216 of the 2,400 feeds (9%) advertise a hub, so it would leave out 91% of feeds.

Tomás built it, and it shipped in 0.8.0 on 2 November 2026.

Confidence: high that requests to one host are spaced 10 seconds apart. Not yet known whether the three hosts stay unblocked, because 0.8.0 has run for only a few weeks.

### Consequences

- Good, because one slow or blocking host no longer delays the feeds on other hosts.
- Good, because no host gets a burst of requests.
- Bad, because there is one thread for each host with a feed due, instead of one thread in total. At the peak on Dana's instance, that was 340 threads.
- Bad, because when fetching stops there is no single loop to inspect. `quillfeed fetch-status` was added to list each host's queue.
- Bad, because a host with more than 90 feeds cannot have all of them fetched every 15 minutes. At 10 seconds apart, 150 feeds take 25 minutes.

### Confirmation

`tests/test_fetch_spacing.py` fails if two requests to one host are less than 10 seconds apart.
