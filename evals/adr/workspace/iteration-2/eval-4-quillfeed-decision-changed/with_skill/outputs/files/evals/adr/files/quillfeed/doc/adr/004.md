# ADR 004: Each host has its own fetch queue, with one worker that spaces its requests

## Context and Problem Statement

Feeds change at any time and most give no notice, so Quillfeed polls them, inside its one process (ADR 001). Many feeds share a host: on the maintainer's instance of 2,400 feeds, three hosts each serve more than 150. Fetched back to back, that is 150 requests to one host in about 20 seconds, every 15 minutes. On 6 October 2026 those three hosts answered 429 and then blocked the instance's address for a day. How are feeds fetched so that new articles still arrive quickly and no host is flooded?

## Decision Drivers

- A new article shows up within 15 minutes.
- Requests to one host stay within that host's limits.

No other driver was recorded.

## Considered Options

1. A queue per host, each with one worker that leaves at least 10 seconds between requests to its host, with hosts fetched side by side
2. One poller that walks every feed in turn and sleeps 10 seconds between two feeds on the same host
3. No polling: subscribe with WebSub, so hosts push new articles

## Decision Outcome

Chosen: option 1, decided by Dana on 19 October 2026, because it is the only option that keeps both the 15-minute promise and the hosts' limits. Option 2 lost because it breaks the 15-minute promise: Tomás ran it against the maintainer's 2,400 feeds, and one walk went from 6 minutes to 70. Option 3 lost because only 216 of those feeds (9%) advertise a hub, so it leaves out 91% of them. How it works is in [doc/design/fetching.md](../design/fetching.md).

Confidence: the deciders didn't state one. Option 1 shipped in 0.8.0 on 2 November 2026 and runs on the maintainer's instance. Its spacing is tested. No measurement shows that it keeps every feed within 15 minutes, or that the hosts which blocked the instance no longer do.

### Consequences

- Good, because no host gets more than one request every 10 seconds.
- Good, because a slow host delays only its own feeds, since hosts are fetched side by side.
- Bad, because there is one thread for each host with something due: 340 at the peak on the maintainer's instance, where there used to be one.
- Bad, because when fetching stops there is no single loop to look at. `quillfeed fetch-status` lists each host's queue for whoever is finding out why.

### Confirmation

`tests/test_fetch_spacing.py` fails if a host's worker makes two requests without waiting `SPACING_SECONDS` (10) between them. Nothing checks that hosts are fetched side by side or that a feed is fetched again within 15 minutes.
