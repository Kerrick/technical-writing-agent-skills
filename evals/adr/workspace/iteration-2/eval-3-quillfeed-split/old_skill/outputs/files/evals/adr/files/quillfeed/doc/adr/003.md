# ADR 003: Article bodies are compressed files on disk, indexed in SQLite

## Context and Problem Statement

Quillfeed keeps every article it fetches. This lets the reader work when the feed's host is offline, and lets search find articles the feed has since dropped. An article is a few fields (title, link, author, dates) and a body of HTML, from 1 KB to several megabytes. Everything else Quillfeed stores is in the SQLite database (ADR 001). Where do article bodies go?

## Decision Drivers

- The database stays small enough to copy while Quillfeed runs.
- Reading one article is one lookup.
- A host with a small disk can cap how much Quillfeed keeps.

## Considered Options

1. Bodies as zstd-compressed files on disk, with one row per article in SQLite that holds the fields and the file's name
2. Bodies as BLOB columns in the SQLite database
3. Bodies in an S3-compatible object store

## Decision Outcome

Chosen: option 1, because it alone keeps the database small. With the maintainer's 2,400 feeds, a year of bodies as BLOBs made a 41 GB database that took 19 minutes to copy. With bodies as files, the database was 310 MB and copied in 9 seconds. Option 3 lost because it adds a service the host must run, which goes against ADR 001's drivers.

Confidence: high that it works, because the maintainer's instance has run this way since April. Medium that it is better than option 2 for a small instance, where the database would stay small either way.

### Consequences

- Good, because the database copies in seconds, so a backup can run every hour.
- Good, because a host can free space by deleting old body files, and Quillfeed shows those articles as "body no longer kept".
- Bad, because a backup is now two things, the database and the bodies folder. They can be copied at different moments, which leaves rows whose file is missing.
- Bad, because nothing makes a row and its file change together: a crash between writing the file and the row leaves a file that no row names.

### Confirmation

No test checks this yet. `tests/test_store.py` checks only where a body's file goes. A test that writes an article and fails if the database grows by more than 2 KB would confirm it.

## More Information

Evidence: with bodies as BLOBs, the nightly backup took longer each week. On 2 April it overlapped the morning fetch, and the reader stalled for 11 minutes. Bodies as uncompressed files made a 38 GB bodies folder. zstd made it 14 GB at level 3 and 11 GB at level 9, and level 9 added 4 ms to storing an article.

The table layout, file naming, retention, and nightly cleanup are in [doc/design/storage.md](../design/storage.md).
