# Sets and sequences: docs sites, landing pages, series, books, courses

Read this when writing or restructuring anything made of several pages: a docs site or section, a landing or navigation page, a tutorial series, a book, or a course.

## Rules

**Give the docs a map and each section a landing page.** Give the documentation an explicit map: which kinds of page exist, what each is for, where beginners start, and how much ground the introductory material covers. Give each section or multi-page unit a landing page: a short summary of the area, then a structured list of its child pages with one line on what each covers. A unit overview can preview each topic in a sentence or two with a small example, and end with two exits: "work through this in order" and "skip to the next unit if this is familiar." Where a section's readers arrive in different situations or with different goals, send each kind of reader to a different starting point.

**Sequenced pages may build on earlier ones.** Pages in a deliberately ordered learning path (a tutorial series, book, course, or sequenced conceptual pages) may depend on earlier pages, including a running example carried across them. Each such page links back to what it relies on and restates the starting code it builds on, so a reader arriving from search can follow. Serve readers who want to look something up with separate lookup sections, rather than making every lesson self-contained.

**Bridge gaps in assumed knowledge.** When the material relies on things some readers may not know (features within a skill they're assumed to have, or basics only some readers have), add a dedicated bridging section or chapter. It covers only those things, links out for the rest, says who can skip it, and says readers can come back to it when stuck. In a book, you may also mark the late chapters as reference, and offer an alternative reading order for readers who want detail before practice.

**Say where to get help.** Tell readers where to get help from people at the start of each part of a multi-part tutorial, and right after the first step likely to fail. Where there are several channels, say which to try first. Early in the documentation, say how to report a mistake in it.

## Gotchas

- Writing content pages with no entry points, so readers can't tell where to start, what's there, or what they can skip.
- Making every lesson fully self-contained, repeating setup and context until the sequence is bloated.
- Assuming prerequisite features and losing part of the audience, or scattering remedial asides through every chapter.
- Leaving stuck readers with nowhere to turn, and giving doc bugs no route to the maintainers.
